## Ce qui est sain

Il faut le dire avant le reste, parce que c'est l'essentiel.

- **Le solveur est exact.** Programmation dynamique sur les valeurs 1 à 13,
  état borné par les deux exemplaires de chaque carte, énumération des As hauts
  couleur par couleur. Ce n'est pas une heuristique : il trouve vraiment le
  maximum. L'encodage d'état (`n * 20000000 + encode(st)`, base 4 sur 12 chiffres
  = 16,7 M < 20 M) ne peut pas entrer en collision.
- **Les six langues sont complètes.** 209 clés, zéro manquante, zéro en trop
  dans les cinq traductions. C'est rare et ça mérite d'être noté.
- **Aucune donnée ne sort de l'appareil.** Pas une requête réseau, pas de
  télémétrie, pas de compte. Le journal de débogage est affiché pour être copié
  à la main, jamais transmis.
- **Pas de dépendance.** Ni npm, ni CDN, ni framework : aucune chaîne
  d'approvisionnement à surveiller, aucune bibliothèque à mettre à jour.
- **Le moteur et l'interface sont séparés proprement.** `engine.js` ne connaît
  pas le DOM, `solver.js` ne connaît pas le moteur.

## Sécurité

Le contexte limite d'emblée la gravité : jeu solitaire, local, sans compte ni
secret. Rien de ce qui suit ne met en danger des données personnelles. Mais le
premier point est une vraie faille, pas une hypothèse.

### S1 — Injection de code par un journal rejoué `[vérifié]` ✅ corrigé

Les noms des joueurs virtuels d'un journal sont écrits dans le DOM sans
échappement (`ui.js:1215`, `ui.js:1250`, `ui.js:275`).

Preuve exécutée dans le bac à sable :

```js
RC.rejouer({ donne: { n: 1, order: […], names: ['<img src=x onerror="…">'] }, … })
// → le code s'exécute
```

Pire, **ça persiste** : `newGame()` écrit `prefs.lastDeal = game.deal`, noms
compris, dans `localStorage`. Après rechargement de la page, le bouton
« Rejouer la donne précédente » réexécute la charge. Vérifié.

Le chemin d'attaque est étroit — il faut que tu colles toi-même un journal
reçu de quelqu'un d'autre — mais c'est précisément l'usage prévu de cette
fonction.

**Correctif** — échapper au rendu *et* valider à l'entrée :

```js
function echapper(s) {
  return String(s).replace(/[&<>"]/g, function (c) {
    return { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;' }[c];
  });
}
```

et, dans `Game()`, n'accepter que des noms courts et sans balise, ou mieux :
ne garder du journal que des **indices** dans `AI_NAMES`, jamais des chaînes
libres. C'est la correction la plus robuste : plus aucune chaîne étrangère
n'entre dans le jeu.

**Fait** — `echapper()` appliqué aux **six** endroits où un nom entre dans la
page : avatar et nom de la rangée des joueurs, bandeau compact (nom entier et
initiale), titre et sous-titre du panneau de fin, lignes du classement.
Revérifié avec la même charge : aucune exécution, aucune balise injectée, le
nom s'affiche en toutes lettres. La validation à l'entrée du journal reste à
faire (proposition 7) — c'est elle qui fermerait la porte, l'échappement ne
fait que la rendre inoffensive.

### S2 — Les réglages sont réinjectés en JavaScript brut ✅ corrigé

`main.swift:58` :

```swift
"window.APP_PREFS=\(saved);"
```

`saved` est le JSON lu dans `UserDefaults`, concaténé tel quel dans un script
exécuté au chargement. L'app n'étant pas en bac à sable, n'importe quel
processus de ta session peut écrire :

```bash
defaults write com.rboulais.rummicard RCPreferences '<javascript arbitraire>'
```

et obtenir l'exécution de ce code dans la WebView au prochain lancement.

Il faut déjà un accès local pour en profiter — mais la correction tient en une
ligne, et `jsLiteral()` existe déjà juste au-dessus :

```swift
"try{window.APP_PREFS=JSON.parse(\(jsLiteral(saved)));}" +
"catch(e){window.APP_PREFS=null;}"
```

**Fait.** Six cas tordus passés au banc d'essai — guillemets, antislashs,
retours ligne, `" ; alert(1) ; "`, `</script><img onerror>` — tous ressortent
en **donnée**, aucun en code. Une valeur qui n'est pas du JSON valide mène
désormais au `catch` au lieu d'être exécutée.

### S3 — Pas de politique de sécurité du contenu `[à faire — proposition 8]`

`index.html` n'a pas de `Content-Security-Policy`. Le jeu n'a aucune ressource
externe : la règle serait donc à la fois stricte et sans effet de bord, et
elle neutraliserait à elle seule l'essentiel de S1.

```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; img-src 'self' data:; style-src 'self';
               script-src 'self'; connect-src 'self'; base-uri 'none'">
```

À vérifier sur l'hôte macOS, qui charge en `file://` — la règle `'self'` s'y
comporte différemment ; un essai s'impose avant de généraliser.

### S4 — API privées par KVC dans l'hôte natif `[à faire — proposition 9]`

`main.swift:47` et `:69` :

```swift
config.preferences.setValue(true, forKey: "developerExtrasEnabled")
web.setValue(false, forKey: "drawsBackground")
```

Ce ne sont pas des failles mais des **fragilités** : ces clés ne font pas partie
de l'API publique et peuvent disparaître à une mise à jour de macOS — avec, pour
le `setValue` sur une clé inconnue, un plantage au lancement. L'inspecteur web
a d'ailleurs un équivalent public depuis macOS 13.3 :

```swift
if #available(macOS 13.3, *) { web.isInspectable = true }
web.underPageBackgroundColor = .clear   // remplace drawsBackground
```

## Fonctionnalité

### F1 — Les raccourcis se déclenchent avec ⌘ `[vérifié]` ✅ corrigé

`ui.js`, gestionnaire `keydown` : aucun test sur `metaKey` / `ctrlKey` / `altKey`.

Mesuré : **⌘P ouvre la boîte d'impression *et* pioche une carte**, ce qui met
fin au tour. Idem pour ⌘T (nouvel onglet + changement de tri), ⌘R, ⌘I, ⌘M.

C'est le défaut le plus concret de cet audit : une frappe banale fait perdre un
tour, et la pioche n'est pas annulable par ↩.

**Correctif** — une ligne :

```js
if (e.metaKey || e.ctrlKey || e.altKey) return;
```

**Fait.** Revérifié : ⌘P, ⌃P et ⌥P ne piochent plus, ⌘T ne change plus le tri,
et `T` seul continue de fonctionner.

### F2 — Une exception pendant le tour des joueurs virtuels fige la partie ✅ corrigé

`aiPhase()` est `async` et sans `try`. Si `AI.playAITurn` lève — cas limite du
solveur, état corrompu — `busy` reste à `true` **définitivement** : plus aucun
bouton ne répond, aucun message n'apparaît, et rien dans l'interface ne dit ce
qui s'est passé. Il faut relancer l'app.

```js
async function aiPhase() {
  busy = true;
  try { /* … boucle … */ }
  catch (e) { toast(TR('err.interne')); if (prefs.debug) console.error(e); }
  finally { busy = false; render(); updateBar(); }
}
```

C'est peu probable, mais le coût d'un `finally` est nul et le symptôme, sans
lui, est le pire possible : un gel muet.

**Fait — et le correctif ci-dessus ne suffisait pas.** À l'essai, avec une
panne simulée, le message s'affichait et `busy` retombait, mais **le tour
appartenait toujours au joueur virtuel en faute** : `isHumanTurn()` restait
faux, la barre restait éteinte, la partie restait bloquée. Relâcher le drapeau
ne rend pas la main. Le joueur fautif passe donc son tour et l'on avance
jusqu'au joueur humain :

```js
var sauts = 0;
while (!game.finished && !game.player().human && sauts++ <= game.players.length) {
  game.pass();
  game.nextPlayer();
}
```

Revérifié : message affiché, tour rendu, et la partie se poursuit
normalement ensuite. Nouvelle clé `err.interne` dans les six langues.

### F3 — Un journal malformé corrompt la partie en silence

`cardFromId('9-99-7')` fabrique une carte de couleur 9 et de valeur 99 sans
protester. `Game()` ne vérifie que `order.length === 104` — ni les valeurs, ni
l'absence de doublons. Résultat affiché : `undefinedundefined`.

Une validation de la donne à l'entrée de `rejouerJournal` réglerait F3 et
contribuerait à S1.

### F4 — Égalité : le joueur humain gagne toujours

`engine.js`, `lowestHand()` part de `players[0]` — toi — et compare avec un `<`
strict. À nombre de points égal en fin de pioche, **tu l'emportes**. Même
logique dans `roundScores()`.

Peut-être voulu. Si ce n'est pas le cas, c'est à décider plutôt qu'à subir :
égalité déclarée, ou départage sur le nombre de cartes.

### F5 — Deux reliquats sans effet

- `snapshot.melded` est enregistré par `beginTurn()` mais `restoreTurn()` ne le
  relit jamais. Champ mort.
- `p.melded` ne gouverne **aucune règle** : il n'alimente que l'étiquette
  « en jeu » / « à poser » de la rangée des joueurs. Or « à poser » laisse
  entendre une obligation d'ouverture personnelle qui n'existe pas dans cette
  variante — la seule contrainte porte sur la table vide, pas sur le joueur.
  Le mot induit en erreur.

### F6 — Environ 60 lignes de traduction mortes

Reliquats des fonctions retirées ces derniers jours, dans les six langues :
`hud.tour`, `hud.reflechissent`, `bar.glisser`, `toast.tapis`, `fold.*` (4),
`accueil.langue`, `hud.termine`, `hud.pose`, `hud.main`.

Sans conséquence, mais chaque clé morte est un piège pour la prochaine lecture.

## Ergonomie

### E1 — Accessibilité : quasi inexistante

Un seul `aria-label` dans tout le projet (les pastilles de tapis, ajoutées
aujourd'hui). Concrètement :

- les cartes ne sont ni focalisables ni annoncées : **le jeu est injouable au
  lecteur d'écran et injouable au clavier seul** (les raccourcis couvrent les
  actions, pas le placement des cartes) ;
- `user-scalable=no, maximum-scale=1` dans la balise `viewport` **interdit le
  zoom à deux doigts**. En PWA installée sur iPhone, iOS respecte cette
  interdiction. Pour qui a besoin d'agrandir, il n'y a pas de recours ;
- ~~aucun `@media (prefers-reduced-motion: reduce)`~~ **✅ corrigé.** Attention
  au piège : la règle CSS ne touche **pas** les animations FLIP, créées en
  JavaScript par `element.animate()`, qui échappent entièrement à la feuille de
  style. Il a fallu les court-circuiter aussi (`mouvementReduit()` dans
  `flip()`), sans quoi les cartes auraient continué de glisser d'un bout à
  l'autre de la table. Mesuré : 14 animations au lancement d'une partie,
  **0** en mode réduit.

Le point du mouvement réduit est traité. Le zoom reste ouvert (proposition 11).
Le premier point — clavier et lecteur d'écran — est un chantier à part entière,
à n'ouvrir que si tu en as l'usage.

Un point positif : les quatre couleurs sont distinctes (♠ ardoise, ♥ rouge,
♦ bleu, ♣ vert) **et** portent leur symbole. L'information n'est jamais portée
par la seule couleur.

### E2 — La pioche est irréversible et le recours est discret

« Piocher » termine le tour immédiatement, sans confirmation. ↩ (« Annuler »)
ne défait que les poses du tour, pas la pioche. Le seul recours est
« Refaire mon tour », qui remonte au début du tour précédent — mais rien ne
l'indique au moment où on en a besoin.

Deux pistes, par ordre de discrétion : mentionner « Refaire » dans le message
qui suit une pioche, ou demander confirmation quand on pioche alors qu'un coup
était possible (l'information est déjà calculée en mode Indices).

### E3 — Le solveur tourne sur le fil principal

Mesuré sur ce Mac : **45 ms** pour une table résoluble de 80 cartes. Sur iPhone,
compter trois à cinq fois plus, soit ~150 à 200 ms — pendant lesquels l'écran ne
répond pas. C'est appelé à chaque changement de table en mode Indices, et une
fois par glisser.

Ça reste sous le seuil de l'agacement aujourd'hui. À surveiller : le coût croît
avec le remplissage de la table, et c'est en fin de manche — table pleine, main
réduite — qu'on sollicite le plus les indices. Si ça devenait gênant, un Web
Worker réglerait la question sans toucher au solveur lui-même.

### E4 — Les boutons du panneau natif ne sont pas traduits ✅ corrigé

`main.swift`, `runJavaScriptConfirmPanel` : « Continuer » / « Annuler » sont
écrits en dur, alors que tout le reste de l'hôte est traduit en six langues.
Visible à chaque abandon de partie dans une autre langue que le français.

**Fait** — clés `continuer` et `renoncer` ajoutées aux six tables de `MENUS`.
